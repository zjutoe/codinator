# Pi 主界面协议 v1

一次明确启动已发布的任务后，Pi + `bonsai/bonsai2-27b/xhigh` 可自动实施、提交、等待 Codex、返工和再次提交。只有独立 Codex 的 `accepted` 可结束验收；无需逐轮用户确认。轮次耗尽、范围/证据变化、服务故障或用户中止会暂停，不保证任何任务必然被接受。

入口为 `codinator pi MANIFEST`，恢复为 `codinator pi TASK_ID --resume`。用户直接看到原生 Pi TUI；控制器在旁路运行，没有第二个无头 Pi。`/codex-pause` 中断自动循环，`/codex-resume` 显式恢复，`/codex-status` 查看证据路径。原有 run/serve 继续兼容，两种入口使用相同的工作目录互斥锁，但状态位于独立 `interactive/` 子目录，旧后台服务不会接管交互任务。

Pi 扩展只注册任务提交工具和上述命令。提交工具接收 Markdown 正式总结，先终止本批工具后的自动续答，在 `agent_settled` 后提交，避免并行工具未写完时快照。后台生成带任务、轮次、快照摘要的 `submission.md`，程序记录提交成功；不依赖模型另写 completion.json。同一提交 ID 重复发送不会重复派发审查。

控制器对实际工作树取快照、校验范围、保留内容，执行原合同检查，然后复用独立 Codex 审查器。正式结果是 `review.md`，机器状态仍由控制器写入 SQLite。原始事件、认证副本、会话文件放在仓外，不混进总结。审查意见明确署名 Codex，不能作为用户扩大任务权限的授权。检查失败会产生明确署名控制器的返工意见。

Pi 和 Codex 都保持 bubblewrap 边界。Pi 只可修改允许路径，Git 元数据、交接和历史只读；提交后扩展拒绝继续使用实施工具。人工或其他进程仍可能修改文件，因此检查/审查完成后再次比对快照，有变化拒绝旧结论。所有阶段共用工作目录锁。通信是本机 Unix socket，只有 submit/status/pause/resume/start 等有限操作，没有接受接口或任意命令入口。

Pi 进程去掉 proxy，Codex 继承启动控制器时的 proxy。新交互模式中人机讨论没有任务总墙钟；每次 Codex 调用使用 manifest 的 attempt_seconds（默认 7200），每个检查使用自己的超时，轮次仍受 max_rounds 限制。旧模式 max_seconds 行为不变。

退出 Pi 或控制器中断时保留现场，不自动重放不确定提示。显式恢复实施会从留下的局部工作继续；已成功检查且进入审查的冻结提交，恢复只重试审查。原始 RUN 永不覆盖，已有 verdict 但未完成状态落盘须人工核对。会话恢复会重新给出原契约和最近正式意见。

### 2026-09-28 返工状态修正

交互和后台模式均按 `max_rounds` 限制自动返工；`needs_changes` 的 issue ID 即使连续相同，也应在剩余轮次内交回 Pi。审查器要求沿用稳定 ID，部分修复仍使用相同 ID，因此 ID 集合不作为“无进展”的判断。独立审查仍可明确返回 `blocked`；范围、快照、证据、模型和预算限制继续生效。

旧交互任务因相同 issue ID 被置为 `blocked / feedback` 时，显式 `resume` 可恢复为 `needs_changes` 并将 round 加一。恢复前核对当前快照、原检查证据摘要和正式返工结论，必须仍有剩余轮次；事务记录状态转换，旧 attempt 不改写或重放。Pi 下次提交创建新 attempt。`paused / feedback` 已经计入下一轮，恢复时不再增加 round。其他 `blocked / feedback`（包括审查者明确阻塞或轮数耗尽）不由此入口解除。更新 Python 控制器代码后需重启旧原生 Pi 会话才能使用新逻辑。

### 提交拒收、暂停原因与字节码缓存

`codex_submit_review` 的工具返回只表示本地请求排队；`interactive_submitted` 事务事件才是正式收据。冻结前的范围错误使用明确的 `submission_rejected` 响应，保留请求／当前快照／内容和 `interactive_submission_rejected` 事件；不新建审查 attempt、不增加 round、不覆盖最近正式 review。Pi 收到明确拒收后允许在原范围内修复并用新工具调用提交一次。再次拒收会暂停；需要修改契约或冻结文件的问题仍交由 Codex，不能据错误信息扩大权限。

只有这个已知的提交前边界会返回明确拒收。存储失败、网络故障、提交事务后的错误等均视为结果不确定，不自动重放请求。暂停立即冻结本地工具及轮询；即使暂停 RPC 也失败，Pi 会话仍保存原因，等待明确恢复。成功或失败回执晚到时不能撤销用户暂停／中止。暂停原因通过 bridge 保存到 SQLite，控制器和会话收尾不能用笼统退出原因覆盖它。

原生 Pi 继承 `PYTHONDONTWRITEBYTECODE=1`，并将 `PYTHONPYCACHEPREFIX` 指向仓外私有配置目录的 `pycache`；显式编译也应使用仓外输出。`-I` 会忽略 Python 环境变量，因此依旧要求子进程显式 `-B`。

原生提交及显式恢复实施的预检只对以下派生物执行清理：发布后新建、白名单之外、直接位于 `__pycache__`、带控制器解释器实际 `cache_tag` 和 magic 的 `.pyc`，源码为对应目录中的普通 `.py` 文件，缓存为单链接普通文件。未知版本／错误头部、已有或被修改的基线缓存、符号链接、硬链接、其他越界改动、Git 或根目录变化均不自动处理。`.gitignore` 不是快照排除规则。仅当去掉候选缓存后的投影快照完全通过原范围检查时才继续。

清理使用新的 `cache-cleanup-*` 目录：先将完整现场保存为 `before.json` 和不可变 blobs，写清理清单，再复核现场，将实际缓存重命名到仓外 `removed/`，只删除新建且已空的缓存目录，最后核对并记录 `after.json`。中途失败保留所有已归档／未移动的字节，下次显式恢复新建记录；不同文件系统的 rename 失败时不使用复制后删除作为回退。已有 attempt、manifest、验收条件不变。冻结的检查／审查状态不做此清理，仍要求原提交快照一致。后台 run/serve 的现有提交与恢复流程不受此交互协议修改。

验收需要：自动首轮→返工→接受；重复提交不重复执行；暂停/退出/进程失败恢复；旧结论、越界和伪造接受被拒；代理隔离；原生 Pi 扩展加载、工具与命令存在；现有流程回归。模拟检查与真实模型联调分别记录。活动中的 T0017 不迁移、不打断。
